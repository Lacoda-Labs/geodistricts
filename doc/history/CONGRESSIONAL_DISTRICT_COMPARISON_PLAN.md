# Congressional District Comparison Plan

## Executive Summary

This document outlines a comprehensive plan to fetch, process, and compare existing US congressional district maps with geodistricts maps. The goal is to enable district-by-district comparisons at the state level, analyze voter registration party balance changes, compare racial demographic data between current congressional districts and algorithmically-generated geodistricts, and generate national-level summary comparisons aggregating all 50 states plus DC. The national comparison will include single-district states (AK, DE, MT, ND, SD, VT, WY, DC) to provide a complete United States overview.

## Objectives

1. **Fetch existing US congressional district map data** for all states (including single-district states for national comparison)
2. **Compare geodistricts maps with current congressional district maps** at state and national levels
3. **Match overlapping districts** between current and geodistrict maps (for multi-district states)
4. **Collect and aggregate voter registration data** for both district types
5. **Compare party balance changes** resulting from geodistrict maps (state and national levels)
6. **Collect and compare race demographic data** for both district types (state and national levels)
7. **Generate national-level summary comparisons** aggregating all states
8. **Identify issues and challenges** that may affect comparison accuracy

## 1. Data Acquisition

### 1.1 Existing Congressional District Maps

#### 1.1.1 Primary Data Source: US Census Bureau TIGER/Line Shapefiles

**Source**: U.S. Census Bureau TIGER/Line Shapefiles  
**URL**: https://www.census.gov/geographies/mapping-files/time-series/geo/tiger-line-file.html  
**Format**: Shapefiles (.shp) or GeoJSON  
**Coverage**: All 50 states + DC  
**Update Frequency**: Updated after each decennial census and redistricting cycle

**Access Methods**:
- **Direct Download**: Download shapefiles from Census Bureau FTP site
  - FTP: `ftp://ftp2.census.gov/geo/tiger/TIGER2020/CD/`
  - HTTP: `https://www2.census.gov/geo/tiger/TIGER2020/CD/`
- **TIGERweb REST API**: Access via ArcGIS REST services
  - Base URL: `https://tigerweb.geo.census.gov/arcgis/rest/services/TIGERweb/tigerWMS_Current/MapServer`
  - Layer: Congressional Districts (116th Congress and later)
- **Alternative**: Use Census Bureau's Cartographic Boundary Files (simplified boundaries)
  - URL: `https://www.census.gov/geographies/mapping-files/time-series/geo/cartographic-boundary.html`

**Data Structure**:
- Each state has a separate shapefile
- Districts identified by `CD116FP` or `CD118FP` (116th/118th Congress district number)
- State FIPS code in `STATEFP`
- GEOID format: `STATEFP + CD116FP` (e.g., "0601" for California District 1)

**Implementation Notes**:
- **All states must be collected** (including single-district states: AK, DE, ND, SD, VT, WY, DC) for national-level comparison
- Single-district states don't require district matching but still need data aggregation for national summaries
- **Note**: Montana (MT) has 2 districts and requires matching like other multi-district states
- Need to handle multiple redistricting cycles (2020, 2022, etc.)
- Some states may have multiple valid district maps due to court-ordered redistricting
- **Important**: Congressional districts are built from census blocks (smallest unit), not census tracts. Districts can split census tracts, which affects matching and data aggregation strategies (see Section 2.2.1)

#### 1.1.2 Alternative Data Sources

**PlanScore API** (if available):
- Provides standardized congressional district maps
- May include historical redistricting data
- URL: Check PlanScore.org API documentation

**State-Specific Sources**:
- Some states provide their own shapefiles on state GIS portals
- May include more recent redistricting updates than Census Bureau
- Examples:
  - California: https://statewidedatabase.org/
  - Texas: https://www.tlc.texas.gov/
  - New York: https://gis.ny.gov/

### 1.2 Geodistricts Map Data

**Current Implementation**:
- Geodistricts are generated by the algorithm in `backend/services/geodistrict-algorithm.js`
- Output format: GeoJSON with district groups containing census tracts
- Each district group has:
  - `startDistrictNumber` and `endDistrictNumber`
  - `censusTracts`: Array of GeoJSON features
  - `totalPopulation`: Aggregated population
  - `bounds`: Geographic bounds
  - `centroid`: Population-weighted centroid

**Data Format**:
- Currently stored in algorithm results
- Need to convert to standard GeoJSON format for comparison
- Each geodistrict should be a single GeoJSON feature with:
  - `properties.districtNumber`: Assigned district number (after matching)
  - `properties.state`: State abbreviation
  - `properties.totalPopulation`: District population
  - `geometry`: Combined geometry of all tracts in district

**Storage Requirements**:
- Store geodistrict maps in Cloud Storage (similar to tract boundaries)
- Cache key format: `geodistricts/{state}/{algorithm_version}/{timestamp}.geojson`
- Include metadata: algorithm version, generation timestamp, state, district count

#### 1.3.2 Data Aggregation Strategy

**For Existing Congressional Districts**:
- Use provided district-level statistics directly (if available)
- If only county-level data available:
  - Use spatial intersection to allocate county voter registration proportionally
  - Formula: `district_voters = county_voters * (district_area_in_county / total_county_area)`
  - More accurate: Use population-weighted allocation
- **Note on split tracts**: If districts split census tracts (which can occur), tract-level aggregation may not be accurate. Use spatial intersection to allocate tract data proportionally based on area or population overlap.

**For Geodistricts**:
- **Method 1**: Aggregate from census tract level (if tract-level data available)
  - Sum voter registration across all tracts in geodistrict
- **Method 2**: Use spatial intersection with existing district data
  - Intersect geodistrict boundaries with existing congressional districts
  - Allocate voter registration proportionally based on overlap area or population
- **Method 3**: Use precinct-level data (if available)
  - Map precincts to census tracts
  - Aggregate precinct data to geodistricts

**Data Variables Needed**:
- Total registered voters
- Democratic registered voters
- Republican registered voters
- Other/Independent registered voters
- Date of registration snapshot

- **Existing Districts**: Aggregate tract-level data to district boundaries

  - If district splits tracts: Use spatial intersection to allocate tract data proportionally based on area or population overlap
  - Calculate percentages from aggregated totals
- **Geodistricts**: Aggregate tract data to geodistrict boundaries
  - Geodistricts use whole tracts (algorithm constraint), so simple summation works
  - Use tract membership from algorithm results
  - Sum demographic variables across all tracts in geodistrict

#### 1.4.2 Data Processing

**For Both District Types**:
1. Fetch demographic data for all census tracts in state
2. Group tracts by district (existing or geodistrict)
   - **For existing districts**: Handle split tracts using spatial intersection if needed
   - **For geodistricts**: Use whole tract membership (no splits)
3. Sum demographic counts for each district
   - For split tracts, allocate proportionally based on overlap
4. Calculate percentages:
   - `whitePercent = (whiteCount / totalPopulation) * 100`
   - `blackPercent = (blackCount / totalPopulation) * 100`
   - `hispanicPercent = (hispanicCount / totalPopulation) * 100`
   - etc.

**Caching Strategy**:
- Cache tract-level demographic data (already implemented)
- Cache district-level aggregations
- Cache key: `demographics/{state}/{district_type}/{district_number}`

## 2. District Matching and Overlap Analysis

### 2.1 Spatial Intersection Algorithm

**Goal**: Match geodistricts to existing congressional districts based on maximum overlap.

**Approach**:
1. For each geodistrict, calculate spatial intersection with all existing congressional districts
2. Measure overlap using multiple metrics:
   - **Area overlap**: Percentage of geodistrict area that overlaps with existing district
   - **Tract overlap**: Number of common census tracts
   - **Population overlap**: Population in overlapping area
3. Assign geodistrict number based on best match (highest overlap score)

**Overlap Metrics**:

```javascript
// Pseudo-code for overlap calculation
function calculateOverlap(geodistrict, existingDistrict) {
  const intersection = spatialIntersect(geodistrict.geometry, existingDistrict.geometry);
  
  return {
    areaOverlap: (intersection.area / geodistrict.area) * 100,
    tractOverlap: countCommonTracts(geodistrict.tracts, existingDistrict.tracts),
    populationOverlap: sumPopulationInIntersection(intersection),
    overlapScore: weightedScore(areaOverlap, tractOverlap, populationOverlap)
  };
}
```

**Matching Algorithm**:

1. **Initial Matching**:
   - For each geodistrict, find existing district with highest overlap score
   - Create initial mapping: `geodistrict -> existingDistrict`

2. **Conflict Resolution**:
   - If multiple geodistricts map to same existing district:
     - Keep the geodistrict with highest overlap score
     - Reassign other geodistricts to their second-best match
   - If a geodistrict has no clear match (overlap < 30%):
     - Use geographic proximity (centroid distance)
     - Or assign sequential number based on geographic position

3. **Final Assignment**:
   - Assign geodistrict numbers matching existing district numbers where possible
   - For unmatched geodistricts, assign sequential numbers

**Implementation Considerations**:
- Use spatial libraries: Turf.js (JavaScript) or Shapely (Python backend)
- Handle edge cases: districts with very low overlap, split districts
- Consider using existing district numbers as "hints" for geodistrict numbering

### 2.2 Tract-Based Matching (Alternative/Supplement)

**Simpler Approach**: Match based on census tract membership rather than geometry intersection.

**Algorithm**:
1. For each existing congressional district, get list of census tracts
2. For each geodistrict, get list of census tracts (from algorithm results)
3. Calculate Jaccard similarity: `commonTracts / (tractsInGeodistrict + tractsInExisting - commonTracts)`
4. Match geodistrict to existing district with highest Jaccard similarity

**Advantages**:
- Faster computation (no geometry intersection)
- More reliable for districts with many small tracts
- Works well when tract boundaries align with district boundaries

**Disadvantages**:
- Less accurate when districts split tracts (rare but possible)
- Doesn't account for partial tract overlaps

### 2.2.1 Important Note: Census Tracts vs Census Blocks

**Critical Understanding**: Congressional districts are built from **census blocks** (the smallest geographic unit), not census tracts. While districts can and sometimes do split census tracts, they **cannot split census blocks**.

**Implications**:
- **Tract-based matching is approximate**: Since districts can split tracts, tract membership alone may not perfectly identify district boundaries
- **Block-based matching is more accurate**: For precise matching, we should ideally use census blocks, but this requires:
  - Block-level geometry data (larger files, more processing)
  - Block-level population/demographic data (more API calls)
  - More complex spatial operations

**Practical Approach**:
- **For initial matching**: Use tract-based matching (faster, good approximation)
- **For validation**: Use spatial intersection to handle split tracts
- **For data aggregation**: When tracts are split, use spatial intersection to allocate data proportionally
- **Future enhancement**: Consider block-based matching for states with many split tracts

**Data Availability**:
- Census blocks are available from TIGER/Line: `TIGER2020/TABBLOCK20/`
- Block-level population data available from Census API
- However, block data is significantly larger (millions of blocks vs thousands of tracts per state)

**Recommendation**: Start with tract-based matching supplemented by spatial intersection. If matching accuracy is insufficient (<70%), consider implementing block-based matching for problematic states.

### 2.3 Hybrid Approach (Recommended)

**Combine both methods**:
1. Primary: Use tract-based matching for initial assignment
2. Secondary: Use spatial intersection to resolve conflicts
3. Validation: Check that matched districts have reasonable overlap (>50% area or >60% tracts)

**Final District Numbering**:
- If geodistrict matches existing district with >70% overlap: use existing district number
- If overlap 50-70%: use existing district number but flag as "partial match"
- If overlap <50%: assign new number or use geographic ordering

## 4. Comparison Metrics and Analysis

### 4.1 Party Balance Comparison

**Metrics to Calculate**:

1. **District-Level Party Percentage**:
   - `democraticPercent = (democraticVoters / totalVoters) * 100`
   - `republicanPercent = (republicanVoters / totalVoters) * 100`
   - `otherPercent = (otherVoters / totalVoters) * 100`

2. **State-Level Party Balance**:
   - Total Democratic voters across all districts
   - Total Republican voters across all districts
   - Overall party percentages

3. **Competitive Districts**:
   - Districts with <55% majority party (competitive)
   - Districts with >60% majority party (safe)
   - Count of competitive vs safe districts in existing vs geodistricts

4. **Party Balance Change**:
   - For each matched district pair:
     - `democraticChange = geodistrict.democraticPercent - existing.democraticPercent`
     - `republicanChange = geodistrict.republicanPercent - existing.republicanPercent`
   - State-level change in competitive districts

**Visualization**:
- Bar charts: Party percentages by district (existing vs geodistrict)
- Scatter plot: Democratic % existing vs geodistrict
- Summary cards: Total competitive districts, party balance shift

### 4.2 Demographic Comparison

**Metrics to Calculate**:

1. **District-Level Demographics**:
   - White percentage
   - Black/African American percentage
   - Hispanic/Latino percentage
   - Asian percentage
   - Other race percentages

2. **Majority-Minority Districts**:
   - Districts where minority groups are majority
   - Count of majority-minority districts in existing vs geodistricts
   - Identify districts that gain/lose majority-minority status

3. **Demographic Shift**:
   - For each matched district:
     - Change in each demographic percentage
     - Identify significant shifts (>5 percentage points)

4. **Representation Analysis**:
   - Compare demographic representation in districts
   - Assess if geodistricts maintain or improve minority representation

**Visualization**:
- Stacked bar charts: Demographic composition by district
- Heat maps: Demographic percentages across districts
- Comparison tables: Side-by-side demographic data

### 4.3 Additional Comparison Metrics

**Population Variance**:
- Compare population equality between existing and geodistrict maps
- Geodistricts should have lower variance (algorithm target: <1%)

**Geographic Compactness**:
- Calculate compactness scores (Polsby-Popper, Reock, etc.)
- Compare compactness between existing and geodistrict maps

**Contiguity**:
- Count contiguous vs discontiguous districts
- Compare contiguity between district types

### 4.4 National-Level Summary Comparison

**Goal**: Aggregate comparison data across all 50 states + DC to provide a comprehensive United States summary.

#### 4.4.1 National Party Balance Comparison

**Metrics to Calculate**:

1. **Total National Voter Registration**:
   - Sum all registered voters across all states for existing districts
   - Sum all registered voters across all states for geodistricts
   - Calculate national party percentages:
     - `nationalDemocraticPercent = (totalDemocraticVoters / totalVoters) * 100`
     - `nationalRepublicanPercent = (totalRepublicanVoters / totalVoters) * 100`
     - `nationalOtherPercent = (totalOtherVoters / totalVoters) * 100`

2. **National Competitive Districts**:
   - Count total competitive districts (<55% majority party) in existing vs geodistricts
   - Calculate percentage of competitive districts:
     - `competitivePercent = (competitiveDistricts / totalDistricts) * 100`
   - Compare competitive district counts between existing and geodistrict maps

3. **National Party Balance Change**:
   - Calculate net change in competitive districts
   - Calculate net change in party percentages
   - Identify states with largest party balance shifts

4. **State-by-State Summary**:
   - Table showing party balance for each state (existing vs geodistrict)
   - Highlight states with significant changes (>5 percentage points)
   - Sort by magnitude of change

**Visualization**:
- National summary dashboard with key metrics
- Bar chart: Competitive districts (existing vs geodistrict)
- Pie charts: National party percentages (existing vs geodistrict)
- Map: State-by-state party balance changes (choropleth)
- Table: Detailed state-by-state comparison

## 5. Issues and Challenges

### 5.1 Data Availability Challenges

**Voter Registration Data**:

1. **Inconsistent Granularity**:
   - **Issue**: Most states provide data at county or district level, not tract level
   - **Impact**: Cannot directly aggregate to geodistricts from tract-level data
   - **Mitigation**: 
     - Use spatial intersection to allocate county-level data proportionally
     - Contact state election offices for precinct-level data (if available)
     - Use population-weighted allocation for more accuracy

2. **Update Frequency**:
   - **Issue**: Voter registration data updates monthly/quarterly, may be stale
   - **Impact**: Comparison may not reflect current registration
   - **Mitigation**: 
     - Use most recent available data
     - Document data snapshot date
     - Consider using election results as proxy (if registration unavailable)

3. **Data Format Variations**:
   - **Issue**: Each state provides data in different formats (PDF, Excel, CSV, HTML tables)
   - **Impact**: Requires custom parsers for each state
   - **Mitigation**: 
     - Build state-specific data loaders
     - Create standardized data format
     - Cache parsed data

4. **Missing States**:
   - **Issue**: Some states may not provide public voter registration data
   - **Impact**: Cannot compare party balance for those states
   - **Mitigation**: 
     - Use alternative sources (e.g., academic research, third-party data)
     - Use election results as proxy
     - Clearly document data availability by state

**Congressional District Maps**:

1. **Multiple Valid Maps**:
   - **Issue**: Some states have court-ordered redistricting, multiple valid maps
   - **Impact**: Which map to use for comparison?
   - **Mitigation**: 
     - Use most recent enacted map
     - Document which map is used
     - Consider comparing against multiple maps

2. **Redistricting Cycles**:
   - **Issue**: Districts change after each census and redistricting
   - **Impact**: Need to match geodistricts to correct redistricting cycle
   - **Mitigation**: 
     - Use 2020 census-based districts (current cycle)
     - Document redistricting year
     - Handle state-specific redistricting timelines

### 5.2 Technical Challenges

**Spatial Intersection Performance**:

1. **Issue**: Calculating spatial intersections for large states (e.g., CA with 52 districts) is computationally expensive
2. **Impact**: Slow comparison generation, high server load
3. **Mitigation**: 
   - Use simplified geometries for initial matching
   - Cache intersection results
   - Use tract-based matching first, then refine with geometry
   - Implement parallel processing for large states

**Geometry Accuracy**:

1. **Issue**: Small discrepancies in geometry boundaries can affect overlap calculations
2. **Impact**: Incorrect district matching
3. **Mitigation**: 
   - Use appropriate tolerance for geometry comparisons
   - Validate matches with multiple metrics (area, tracts, population)
   - Handle edge cases (districts with very low overlap)

**Data Synchronization**:

1. **Issue**: Different data sources may use different census tract definitions or FIPS codes
2. **Impact**: Tract-level aggregation may fail
3. **Mitigation**: 
   - Standardize tract identifiers (use GEOID)
   - Validate tract matching before aggregation
   - Handle tract boundary changes between census cycles

### 5.3 Algorithm Integration Challenges

**District Numbering**:

1. **Issue**: Geodistricts are numbered sequentially (1, 2, 3...) but need to match existing district numbers
2. **Impact**: Comparison requires matching step before numbering
3. **Mitigation**: 
   - Implement matching algorithm as final step in geodistrict generation
   - Store both sequential and matched district numbers
   - Allow manual override for edge cases

**Tract Splitting**:

1. **Issue**: Existing congressional districts can and sometimes do split census tracts (districts are built from census blocks, not tracts). Geodistricts use whole tracts only (algorithm constraint).
2. **Impact**: 
   - Cannot use simple tract membership for accurate matching when districts split tracts
   - Tract-based aggregation may be inaccurate for existing districts that split tracts
   - Geodistricts cannot perfectly match districts that split tracts (fundamental limitation)
3. **Mitigation**: 
   - Use geometry-based spatial intersection for accurate matching (handles split tracts)
   - For data aggregation: Use spatial intersection to allocate tract data proportionally based on area or population overlap
   - Consider block-based matching for states with many split tracts (future enhancement)
   - Document which districts split tracts and note limitations in comparison accuracy

**Discontiguous Districts**:

1. **Issue**: Some existing districts are discontiguous (islands, etc.)
2. **Impact**: Overlap calculation may be complex
3. **Mitigation**: 
   - Use spatial libraries that handle MultiPolygon geometries
   - Calculate overlap for each polygon separately, then sum

### 5.4 Data Quality and Validation

**Population Discrepancies**:

1. **Issue**: Population totals may not match between data sources
2. **Impact**: Inaccurate demographic percentages
3. **Mitigation**: 
   - Use consistent population source (Census Bureau)
   - Validate totals match expected state population
   - Document any discrepancies

**Missing Data**:

1. **Issue**: Some tracts or districts may have missing demographic or voter data
2. **Impact**: Incomplete comparisons
3. **Mitigation**: 
   - Flag districts with missing data
   - Use interpolation or estimation where appropriate
   - Clearly document data completeness

### 5.5 Legal and Privacy Considerations

**Voter Registration Privacy**:

1. **Issue**: Voter registration data may have privacy restrictions
2. **Impact**: May not be able to use certain data sources
3. **Mitigation**: 
   - Use only publicly available aggregated data
   - Do not store individual voter records
   - Comply with state data use policies

**Data Attribution**:

1. **Issue**: Need to properly attribute data sources
2. **Impact**: Legal compliance, credibility
3. **Mitigation**: 
   - Include data source attribution in UI
   - Document all data sources in comparison results
   - Include data snapshot dates
