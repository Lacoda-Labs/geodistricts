# 2039 Plan: GeoDistricts Protocol and GitHub Governance

This plan addresses the two pillars in [.cursor/archive/2026-01/260128.md](.cursor/archive/2026-01/260128.md) (2039 Plan) and the refinements in **2124 Plan cont.** and **2151 Plan cont.** (same file): (1) defining the GeoDistricts protocol in detail and positioning it for generative AI use, and (2) defining how to create and maintain the protocol on GitHub with governance and implementer documentation. Execution is **iterative**; the protocol lives in a **separate repo** from this reference implementation.

## Part 1: Defining the GeoDistricts protocol

### 1.1 Modular protocol specification (GDPIPs, not one monolithic spec)

**Goal**: Organize the protocol like NIPs (Nostr) or EIPs/ERCs (Ethereum): many small, atomically maintainable specs. Each improvement or feature is a numbered **GeoDistricts Protocol Improvement Proposal (GDPIP)**; each spec is required or optional and can be versioned and adopted independently.

**Models**: [Nostr NIPs](https://nips.nostr.com/), [Ethereum EIPs](https://eips.ethereum.org/).

**Deliverables**:

- **Protocol structure**: No single monolithic `GEODISTRICTS_PROTOCOL.md`. Instead:
- **Core / required**: A small set of foundational GDPIPs (e.g. data model, required data sources, core algorithm). These define minimal compliance.
- **Optional / extensions**: Separate GDPIPs for demographics aggregation, comparison metrics, optional data sources (voter registration), UI/UX requirements, caching behavior. Implementers and LLMs can pick required + optional sets.
- **Atomic maintenance**: Each GDPIP is one document (or a small, cohesive set); changes are made by revising or superseding that GDPIP, not one big file.
- **Content to distribute across GDPIPs** (from current 1.1): Data model; data sources (required vs optional); algorithm (boundary calculation); demographics for new geodistricts; comparison calculations/metrics. Reference existing [GeodistrictingAlgorithmSpecification.md](https://github.com/Lacoda-Labs/gdip/blob/main/GeodistrictingAlgorithmSpecification.md), [STATE_DATA_SOURCES.md](doc/pages/STATE_DATA_SOURCES.md), [CONGRESSIONAL_DISTRICT_COMPARISON_PLAN.md](doc/history/CONGRESSIONAL_DISTRICT_COMPARISON_PLAN.md), etc., and assign to specific GDPIPs where appropriate.
- **Versioning**: Each GDPIP has a version; protocol “releases” are defined by a set of GDPIP versions (and optional changelog/index).

### 1.2 Generative AI for reference implementations and GDPIP context

**Goal**: Use gen AI to create **reference implementations** (e.g. boundaries for all 50 states, UI/UX, caching). Document how to use this repo as the **reference implementation** of the protocol and how to consume it—plus code, docs, prompt archive/history—in the context of **GDPIPs** (e.g. for LLM context or tooling).

**Deliverables**:

- **Reference implementation**: Explicitly designate this project (geodistricts repo) as the reference implementation of the protocol. Document what it implements (which GDPIPs, required vs optional).
- **Gen AI → reference implementations**: Document how gen AI is used to produce or extend reference implementations (e.g. “produce geodistrict boundaries for all 50 states + DC”; “produce UI that visualizes each algorithm step”; “produce caching design for step navigation”). Tie these to specific GDPIPs where applicable.
- **Documentation for prompting, architecture, deployment, maintaining/improving**:
- **Prompting**: How to prompt (which model, IDE/CLI, context bundle: GDPIPs + optional code/docs/prompt archive).
- **Architecture**: How the reference implementation is structured (backend, frontend, data flow); how new implementations can align.
- **Deployment**: How to run and deploy the reference implementation and derived implementations.
- **Maintaining/improving**: How protocol changes (new GDPIPs, GDPIP updates) flow into the reference implementation and into prompts/context.
- **Context for GDPIP consumption**: Define what is needed so that “this project + GDPIPs” can be consumed as context (e.g. for an LLM): existing code, documentation, prompt archive/history, and any **changes needed** (e.g. index of GDPIPs, context bundle build script, version pins) so that reference implementation and protocol stay in sync.

No execution of LLM code generation is required in this plan; the outcome is the structure (GDPIPs + reference implementation framing) and the documentation that make such generation and consumption possible.

## Part 2: Define to create protocol on GitHub

### 2.0 Separate protocol repository (2151)

**Goal**: This project (geodistricts) is the **reference implementation**, not the protocol repo. The protocol (GDPIPs, governance, index) lives in a **separate GitHub project**. Add explicit recommendations for creating that repo.

**Deliverables**:

- **Recommendations for the new protocol repo**:
- **Purpose**: Host GDPIPs, GDPIP process/governance docs, protocol index/changelog. No application code; spec and process only.
- **Org choice**: Decide whether the protocol repo should live under a **separate org** (e.g. `geodistricts-protocol`) or under **Lacoda-Labs** ([https://github.com/Lacoda-Labs](https://github.com/Lacoda-Labs)). Considerations:
- Lacoda-Labs will host other open source projects (e.g. web3 democracy/NDN protocol, alivevote reference implementation). One org keeps “Lacoda ecosystem” visible; separate org can signal protocol neutrality and multi-implementer ownership.
- Document pros/cons (discoverability, branding, governance perception) and a recommended option.
- **Repo layout**: e.g. `GDPIPs/` (numbered spec files), `process/` (governance, template), `README` with index and link to reference implementation (this repo).
- **Relationship**: Clear doc in both repos: protocol repo = spec + process; geodistricts repo = reference implementation that implements the protocol and links to protocol repo by version/tag.

### 2.1 Protocol improvement process (governance)

**Goal**: Open, transparent process for changing the protocol, inspired by PIP/BIP-style models (e.g. Bitcoin, Ethereum, Solana, Nostr, Bluesky).

**Deliverables**:

- **New repo docs** (in the **protocol repo**; e.g. `process/` or root):
- **GDPIP process**: Numbered **GeoDistricts Protocol Improvement Proposals (GDPIP)** (e.g. GDPIP-001). Template: title, summary, motivation, specification changes, required vs optional, data model/algorithm impact, backward compatibility, reference implementation notes. Align with NIP/EIP-style structure (see 1.1).
- **Governance**: How GDPIPs are submitted (issue + PR), discussed, and adopted (e.g. maintainer merge after comment period); how protocol “releases” are defined by sets of GDPIP versions.
- **Maintenance**: Who maintains the protocol; how GDPIP versions and protocol releases are tagged (e.g. git tags); how changelog/index is updated.
- **CONTRIBUTING.md**: Add a section “Protocol changes” that links to the GDPIP process (in the **protocol repo**) and explains that algorithm/data-model changes require a GDPIP there; this repo tracks protocol versions it implements.
- **Iterative execution (2151)**: Building and executing this plan is **iterative**. Each GDPIP will need review, revision, and edits. The order of work below is a sequence of steps, not one-shot; expect to cycle on GDPIP drafts, feedback, and protocol-repo setup.

### 2.2 Documentation for implementers

**Goal**: Clear paths for state governments, redistricting consultants, and developers to adopt or implement the protocol.

**Deliverables**:

- **Implementer guide**: New doc (e.g. `doc/protocol/IMPLEMENTER_GUIDE.md`) covering:
- Who the protocol is for: state governments, consultants, developers, researchers.
- How to run or integrate: reference backend API, census/TIGER requirements, optional voter data.
- How to verify compliance: population equality, contiguity, and comparison metrics defined in the protocol.
- Links to protocol spec, data sources, and comparison plan.
- **Government and adoption**: Short section or separate doc (e.g. `doc/protocol/GOVERNMENT_AND_ADOPTION.md`) on:
- Research and exploratory use (e.g. academic, pilot comparisons).
- Adoption and codification (e.g. state legislation, reference to “GeoDistricts Protocol” by version; caveats about legal/VRA considerations already noted in project docs).

### 2.3 Doc and repo hygiene

- Promote key plans from `doc/history/` to first-class docs where they define protocol behavior: e.g. [CONGRESSIONAL_DISTRICT_COMPARISON_PLAN.md](doc/history/CONGRESSIONAL_DISTRICT_COMPARISON_PLAN.md), [VOTER_REGISTRATION_DATA_PLAN.md](doc/history/VOTER_REGISTRATION_DATA_PLAN.md) → `doc/pages/` or `doc/protocol/`, and update [GeoDistrictsProjectOverview.md](doc/GeoDistrictsProjectOverview.md) and [.cursorrules](.cursorrules) links.
- Ensure [README.md](README.md) (and any GitHub Pages landing) points to the GDPIP index and implementer guide as the entry points for “implementing GeoDistricts” vs “contributing to this repo”; reference this repo as the reference implementation.

## Suggested order of work

1. **Protocol repo and org** (Part 2.0): Create recommendations doc for the new GitHub protocol repo (org: Lacoda-Labs vs separate; repo layout). Create the repo and add GDPIP process/template and index placeholder so GDPIPs have a home. Iterate on repo setup as needed.
2. **GDPIP process and structure** (Part 2.1): Define GDPIP template, governance, and required vs optional in the **protocol repo**; add GDPIP index so 1.1 has a target. Expect review/revision cycles on each GDPIP.
3. **Modular protocol specs** (Part 1.1): Author initial GDPIPs in the protocol repo (core data model, data sources, algorithm; optional: demographics, comparison metrics). No monolithic spec. Iterative: each GDPIP gets review and revision.
4. **Reference implementation and gen AI docs** (Part 1.2): In **this repo**, document geodistricts as reference implementation and link to protocol repo by version; document prompting, architecture, deployment, maintaining/improving; define context bundle for GDPIP consumption (code, docs, prompt archive/history, and any changes needed).
5. **Implementer and government docs** (Part 2.2): Add implementer guide and government/adoption section (can live in protocol repo or this repo; cross-link); link to GDPIP index and reference implementation.
6. **Doc promotion and links** (Part 2.3): Move or link comparison and voter-registration plans into GDPIP or doc/pages as appropriate; update overview and README in both repos to point to GDPIP index and reference implementation.

## Out of scope for this plan

- Implementing new demographic or comparison features in code (only specifying them in the protocol).
- Building or running LLM code generation (only preparing the protocol and context so it can be done elsewhere).
- Legal or policy advice on VRA or state adoption (only documenting considerations and pointers).
- Changing the existing algorithm implementation; the plan only formalizes the current design into a protocol.
